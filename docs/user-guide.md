# 使用指南

本文介绍 Web 管理后台的日常使用。部署、环境变量和外部 API 细节分别见
[部署文档](deployment.md)、[配置参考](configuration.md)和[API 文档](api.md)。

## 1. 用户角色

| 角色 | 适合人员 | 主要权限 |
| --- | --- | --- |
| 只读 `viewer` | 观察员、运维值班 | 查看仪表盘、频道、消息接入、审核内容、历史和日志 |
| 审核员 `reviewer` | 内容审核人员 | 只读权限 + 编辑、批准、拒绝和发布审核任务 |
| 超级管理员 `super_admin` | 系统管理员 | 用户、频道、接入凭据、规则、设置、系统控制和 API 目标管理 |

首个超级管理员由部署时的 `WEB_ADMIN_USERNAME` 和 `WEB_ADMIN_PASSWORD_HASH` 创建。之后可
在用户管理中创建其他账号。不要让所有日常审核员都使用超级管理员账号。

## 2. 首次配置顺序

推荐按以下顺序配置：

1. 添加 Telegram 或 SafeW 发送目标；
2. 检测 Bot 权限并发送测试消息；
3. 添加来源频道；
4. 在统一选择框中为来源绑定 Telegram、SafeW、API 目标；
5. 选择发布模式；
6. 创建并测试规则；
7. 发送测试来源消息；
8. 在审核队列、消息历史和系统日志中核对结果。

## 3. 频道管理

### 3.1 来源频道

来源代表系统允许接收的 Telegram 频道/群组、SafeW 会话或 API 接入来源。

主要字段：

- **平台**：Telegram、SafeW 或 API 接入；
- **聊天 ID**：Telegram 原始 ID，或 SafeW/API 来源生成的内部 ID；
- **发布模式**：auto、review、rule_based、paused；
- **发送目标**：可混合绑定多个 Telegram 与 SafeW Bot 目标；
- **API 目标**：与机器人目标在同一个选择框中绑定，可绑定多个；
- **启用**：停用后接收端或 sender 忽略新消息。

Telegram 来源可手动输入 ID。常见频道 ID 形如 `-1001234567890`。账号必须已经加入该
频道/群组并具有读取权限。

在单进程模式，Web 可以使用当前 Telethon 客户端扫描账号频道。Compose 拆分模式的 Web
不持有 Telegram 用户客户端，因此“从账户添加”可能不可用，此时应手动添加 ID。

SafeW 来源通常不需要手动创建。首次捕获某个会话通知后，sender 会自动登记来源；管理员
再为它绑定目标。SafeW 的来源标题来自桌面通知，重名会话需通过实际消息谨慎确认。

API 来源在“消息接入”页面创建，通过来源路由链接进入这里配置目标和发布模式。
它不需要 Telegram 账号加入会话，Telegram 可达性检查显示“不适用”。

### 3.2 Telegram 与 SafeW 发送目标

发送目标是 Bot 最终发布消息的 Telegram 或 SafeW 聊天。添加时先选择平台；同一个数值聊天
ID 可以在两个平台分别登记，系统按目标记录和平台隔离路由。

配置步骤：

1. 把 Bot 加入目标频道；
2. 授予发消息权限，发布媒体时也要允许相应内容；
3. 在 Web 添加目标聊天 ID；
4. 点击“检测权限”；
5. 点击“测试消息”；
6. 在来源行绑定该目标。

SafeW 目标的准备步骤相同，但 Bot 需要在 SafeW 的 `@BotFather` 创建，Token 通过 sender 的
`SAFEW_BOT_TOKEN` 环境变量提供。Token 不在 Web 输入，也不会保存在频道数据库。目标列表
中的平台标签和来源行选择器里的 `TG`、`SafeW`、`API` 标签用于区分下游类型。

权限检测与测试消息在 Compose 模式下通过 Redis 命令交给 sender 异步执行。操作后可稍等
并刷新目标状态或查看 sender 日志。

### 3.3 API 目标

API 目标是与 Telegram 目标并列的下游类型。它不会向聊天平台发消息，而是为外部客户端
生成持久化 delivery。

API 目标可以在两个位置管理绑定：

- “对外 API”页面：从目标侧选择多个来源；
- “频道管理”来源行：从来源侧选择多个 API 目标。

只绑定 API 目标、不绑定 Telegram 目标也是有效路由。

### 3.4 删除与停用

- 临时停止接收：停用来源；
- 临时停止某个下游：停用目标或解除绑定；
- 删除来源：不会删除已经存在的消息历史；
- 删除 Telegram/SafeW 发送目标：会清理来源绑定；
- 删除 API 目标：会删除其 Token、来源绑定和 delivery 记录。
- 撤销 API 接入：在“消息接入”撤销凭据，保留来源配置、历史和接收回执。

删除前先确认是否需要保留 API delivery 或审计信息。

## 4. 发布模式

| 模式 | 适用场景 | 行为 |
| --- | --- | --- |
| 自动发布 `auto` | 来源可信、规则稳定 | 未被规则拦截时直接发布 |
| 全部审核 `review` | 新来源、高风险内容 | 所有未拒绝消息都进入审核队列 |
| 规则决定 `rule_based` | 大部分自动、命中规则时审核 | 规则可拒绝或要求审核，否则发布 |
| 暂停发布 `paused` | 维护、临时停止下游 | 完成处理后停在待发布状态 |

全局暂停与来源 `paused` 不同：全局暂停影响整个 sender，来源暂停只影响该来源。

建议新来源先使用 `review`。确认规则和目标正确后，再切换为 `rule_based` 或 `auto`。

## 5. 规则管理

### 5.1 匹配类型

Web 主要提供：

- 关键词；
- 短语；
- 正则表达式；
- 是否包含媒体。

后端还支持 username、link、domain 等规则类型。复杂或版本相关字段可参考当前 OpenAPI。

匹配方式包括包含、完全相等、前缀、后缀和正则。可设置大小写、完整单词、来源范围、
Telegram 目标范围与消息类型。

### 5.2 动作

| 动作 | 作用 |
| --- | --- |
| 标记 `flag` | 记录命中，供审核查看，不直接改变发布结果 |
| 拒绝 `reject` | 停止并过滤消息，不进入 API/Telegram 目标 |
| 要求审核 `require_review` | 强制创建审核任务 |
| 替换 `replace` | 把命中内容替换为指定文本 |
| 移除 `remove` | 删除命中内容 |
| 加标签 `add_tag` | 添加内部标签/命中信息 |

规则按优先级执行。数值越小越先执行。`stop_processing` 会在该规则执行后停止后续数据库规则；
拒绝动作总会停止。

### 5.3 安全上线规则

1. 新建规则时先停用；
2. 使用“测试规则”输入代表性文本和媒体条件；
3. 检查替换后的正文与决策；
4. 启用后让来源保持 `review`；
5. 在规则执行日志确认真实命中；
6. 再切换到 `rule_based`。

规则支持导入、导出和复制。导入前应检查来源/目标 ID 是否适用于当前环境。

## 6. 审核队列

审核任务保存原文、规则处理结果、最终文本、媒体快照、命中规则和操作历史。
API 消息还会显示发送者、会话名称/ID 和外部消息 ID，审核编辑与发布后仍保留这些身份字段。
身份不会自动拼接到最终正文；需要在正文显示时可由采集端提供相应文字或由审核员编辑。

典型操作：

- **编辑**：修改最终发布文本；
- **重跑规则**：基于原文或当前文本重新执行规则；
- **恢复版本**：从历史 revision 恢复；
- **批准**：把任务置为可发布；
- **发布**：批准并发送到当前仍有效的目标；
- **拒绝**：终止任务，不发送 Telegram，不创建 API delivery；
- **批量发布/拒绝**：一次处理多个任务。

审核使用 revision 进行并发保护。如果另一个审核员已经修改任务，当前操作会提示冲突；刷新
详情后重新确认，不要盲目覆盖。

审核任务创建时保存目标快照，发布时还会检查当前绑定：

- 审核期间被停用或解绑的目标不会收到消息；
- 审核期间新绑定的目标不会自动收到这条旧任务；
- 来源被停用后不能继续发布。

## 7. 消息历史

“消息历史”与“审核队列”用途不同：

| 页面 | 展示范围 |
| --- | --- |
| 审核队列 | 进入过人工审核流程的任务 |
| 消息历史 | 所有数据库处理记录，包括 auto、rule_based、过滤、失败和审核发布 |

历史页可以按来源与状态过滤，显示处理后的正文、Telegram 发布数、API delivery 数和时间。
它适合回答“规则自动发布了什么”“为什么没有进审核队列”“哪个下游实际收到了消息”。
API 来源还显示发送者、会话名称/ID 和外部消息 ID；可按发送者与会话 ID 精确过滤，区分
不同聊天中的相同正文。内部消息 ID 为接收回执 ID，采集软件的消息 ID 单独显示。

设置中的“历史落盘”是额外 JSON 文件功能，与消息历史页面无关。即使不启用历史落盘，
数据库历史仍然存在。

## 8. 对外 API

### 8.1 创建

1. 进入“对外 API”；
2. 输入易识别的客户端名称；
3. 设置过期时间，或留空表示永不过期；
4. 选择允许接收的来源；
5. 创建并立即保存 Token。

每个客户端应使用独立 API 目标，以便单独撤销、轮换和审计最后访问时间。

### 8.2 维护

- **停用**：立即拒绝该 Token，并停止创建新 delivery；
- **修改过期时间**：可延长、缩短或设为永不过期；
- **重置 Token**：旧 Token 立即失效，新 Token 只显示一次；
- **修改来源**：只影响之后的新消息，不回填旧消息；
- **删除**：删除该目标的全部 delivery。

客户端接入方式见 [API 文档](api.md)。

## 9. 设置

设置按基础、监听与队列、规则与处理器、审核、历史落盘、Web 分类。

- `hot`：面板表示可在线应用；
- `restart`：保存后需要重启相关容器；
- 密钥字段只读并掩码显示；
- 设置写入 `config/runtime.yaml`。

修改监听、处理器或基础连接配置后，应观察 sender/接收端日志并发送测试消息确认。对生产
系统建议一次只改一组设置。

## 10. 系统状态与日志

仪表盘提供：

- sender、Telegram 接收端、SafeW 接收端心跳；
- Redis 队列长度；
- 待审核、今日接收/发布/失败计数；
- 最近错误与审核任务。

系统日志分为：

- 审核动作日志；
- 处理器执行日志；
- 规则命中日志。

日志页面用于业务审计，容器日志用于进程、网络和第三方 API 排障。两者应结合使用。

## 11. 日常操作建议

- 每天查看失败与重试记录；
- 新规则先测试、再审核观察、最后自动化；
- 定期轮换 API Token 和 Web 管理员密码；
- 定期备份 PostgreSQL 与账号 Session 卷；
- SafeW 客户端更新后重新验证通知标题与正文；
- 升级镜像后检查 migrate 状态、业务心跳和一条端到端测试消息。

## 12. 文字消息接入

### 12.1 创建与配置

1. 超级管理员打开“消息接入”，点击“创建接入来源”；
2. 填写名称，可设置过期时间或先停用接入；
3. 立即保存只显示一次的 Token，关闭后无法再次查看；
4. 点击“配置来源路由”，绑定 Telegram、SafeW 或对外 API 目标，并确认来源启用；
5. 保持默认 `review` 模式发送测试消息，在审核详情核对发送者、会话和正文后再发布。

接入 Token 只用于 `POST /api/ingest/v1/messages`，与对外拉取 Token、Web 登录凭据独立。
来源由 Token 决定，采集软件不能在 JSON 中指定内部来源或发送目标。v1 只接收文字；
“消息接入”页面提供接入地址与可复制的 JSON 示例，完整字段见 [API 文档](api.md#4-消息接入-api)。

多个会话必须使用稳定、不同的 `conversation_id`；每条消息提供会话内唯一的 `message_id`。
`sender` 和 `conversation_name` 用于身份展示，不会自动加到转发正文前面。
`timestamp` 可省略；提供时必须包含时区。
接收正文最长 65,536 字符；现有处理器和 Bot 目标仍可能按 4,096 字符截断，长文本请核对
处理器配置及目标输出。

### 12.2 维护与重试

- **停用接入**：拒绝新提交；频道来源也有独立启用开关，两者均启用才接受新消息；
- **过期时间**：按页面所用本地时区设置，留空表示永不过期；过期后需延长时间才能接入；
- **重新生成 Token**：旧 Token 立即失效，新 Token 只显示一次，需同步更新采集软件；
- **撤销接入**：凭据失效，来源配置、历史和回执保留；
- **只读角色**：可查看接入列表、示例与路由，修改操作仅对超级管理员开放。

`202` 仅表示已入队。相同消息重复提交返回原回执，已入队时为 `200`；同一来源、同一会话、
同一消息 ID 下修改内容会返回 `409`。网络错误或 `503` 时保留原消息 ID、会话 ID 和原内容
重试；首次没传时间的请求，重试时也不要补上新时间。

没有有效发送目标时，接入仍可能成功，但下游处理会在历史中显示路由失败。先修复来源路由，
再由具备 Bot 管理权限的管理员执行 `/retry_failed` 重试失败任务；系统状态页“仅重入队”
恢复的是 `retrying`、`pending_publish` 等可恢复状态，不包含已终止的 `failed`。
再次提交已入队的相同消息只会拿到原回执，不会重跑失败处理。重试后检查历史与审核结果。

升级启用本功能前，需要运行数据库迁移 `0010_api_ingest`（`alembic upgrade head`）。Compose
可执行 `docker compose run --rm migrate`，确认成功后再启动新版 Web/sender。
